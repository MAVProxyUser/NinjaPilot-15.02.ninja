# NinjaPilot Mobile

A phone-sized ground station for the LiteWing board. Five screens: artificial
horizon, thumb-stick flight control, magnetometer diagnostics + calibration,
alarms, and GPS satellite detail. Controller/flight-mode state lives under Fly.

It speaks UAVTalk over UDP to the board's telemetry port (9000), the same
protocol and the same port the desktop GCS uses over Wi-Fi.

## Install

One time, and it cannot be scripted because it needs your Apple ID password:

> Xcode → Settings → Accounts → **+** → Apple ID → sign in

That creates the free "personal team" Apple Development certificate. Then:

```
./tools/deploy.sh
```

It finds the USB-attached iPhone, builds with `-allowProvisioningUpdates` so
the free profile is minted automatically, and installs with `ios-deploy`.
With `WIFI=1` (or no USB phone found) it installs instead over the network with
`devicectl` to the first paired device — that is how the iPhone 16 Pro with the
broken USB port gets it. That phone needs Developer Mode on.

First launch fails until you trust the certificate on the phone:
Settings → General → VPN & Device Management → Developer App → Trust.

**The profile is good for 7 days.** Re-run `deploy.sh` when it expires.

Override the defaults with env vars if you need to:
`BUNDLE_ID`, `DEVELOPMENT_TEAM`, `UDID`.

## Connecting to the board

The phone must be on the same Wi-Fi network as the board. Tap the gear, enter
the board's IP (the desktop GCS was last using `192.168.0.139`), and Connect.

**Only one client at a time.** The firmware latches a single UDP peer and only
hands it over once the current holder has been quiet for 3 seconds
(`pios_wifi.c`). Leave the desktop GCS connected and the two will trade the
stream back and forth, which looks like both of them freezing intermittently.

Connecting raises the telemetry rate on the objects these screens use, and puts
the board's original rates back on disconnect. Force-quitting skips the restore.

## Flying it from the phone

LiteWing has **no RC receiver** — `pios_board.c` maps Throttle/Roll/Pitch/Yaw/
FlightMode to the GCS receiver group on every boot, at the conventional
1000/1500/2000 µs endpoints. Whoever streams the `GCSReceiver` object over the
telemetry socket is the radio. There is no "take control" step and nothing to
switch back afterwards.

The **Fly** tab streams `GCSReceiver` at 50 Hz while "ENGAGE STICKS" is on.
Turn the phone sideways: left thumb is throttle (holds where you leave it,
starts at the bottom) and yaw; right thumb is pitch and roll, spring-centred.
The segmented control is the flight-mode switch, sized from
`ManualControlSettings.FlightModeNumber`. "Board sees" echoes
`ManualControlCommand` back so you can confirm the stream is landing before
you arm. Arming is the board's own stick gesture (`FlightModeSettings.Arming`,
shown on screen) — the app adds no arm button.

Dropping the sticks, backgrounding the app, or losing the link stops the
stream, and `pios_gcsrcvr.c`'s supervisor times the channels out into the
board's failsafe. That is the only failsafe there is: **props off on the bench.**

## Magnetometer

The **Mag** tab shows the one number `filtermag.c` scores —
`|(|mag| − |Be|)| / |Be|` — against the two thresholds it is scored against
(`RevoSettings.MagnetometerMaxDeviation`, stock 5 % Warning / 15 % Critical,
raised after 5 consecutive samples). Watch it move as you move the board:
anything magnetic nearby shows up instantly, and an iPhone's magnets will
push it past 15 % from a few centimetres away.

The calibration is a straight port of the GCS `MagCalibrationModel`
(free-rotation / ellipsoid), including the 1.2 s wait for the cleared
calibration to land before sampling, the bounding-box orientation binning, and
the coverage / residual / radius acceptance tests. It clears the board's
calibration, raises `MagSensor` from its 10 s default to 20 ms, collects until
20 of 26 orientation bins and 2000 samples are in, fits, and offers Save.
Reject or Cancel restores the previous calibration. **Put the phone down 30 cm
from the board before rotating it.**

The thresholds are editable and saveable from the same screen. Loosening them
hides a bad field from the alarm; it does not improve heading.

## Why the protocol layer is generated

`NinjaPilotMobile/Protocol/UAVObjectDefs.swift` is generated by
`tools/gen_uavobjects.py` from `shared/uavobjectdefinition/*.xml`, via
`ground/pyuavtalk`, which is the ground-side source of truth.

Object IDs are a hash over the object's name, its settings/single-instance
flags, and every field name, count, type and enum option. Field order on the
wire is **descending element size**, not XML order. Hand-typing either of those
produces a client that connects happily and then displays nothing, so don't.
Regenerate after any UAVObject change:

```
python3 tools/gen_uavobjects.py
```

The generated IDs were checked against the firmware's own headers in
`build/uavobject-synthetics/flight/` — SystemAlarms `0x6B7639EC`, AttitudeState
`0xD7E0D964`, GPSSatellites `0xC555B700`, FlightStatus `0xEF69B6BC`,
ManualControlCommand `0x161A2C98`, GPSPositionSensor `0x38151688`.

## Build notes

- Deployment target is **iOS 15.0**, arm64. The test phone is an iPhone 8 on
  iOS 16.7.16, which is why `devicectl` is not used — it requires iOS 17+.
- `deploy.sh` builds with `-target`, not `-scheme`, deliberately. This Xcode's
  destination resolver reports "iOS 26.4 is not installed" even though the SDK
  is complete and compiles fine; a target build skips destination resolution.
- Board discovery sweeps the local subnet with unicast UAVTalk requests
  (`BoardDiscovery.swift`), rather than listening for the firmware's
  `NINJAPILOT <ip> <port>` broadcast on UDP 9999.

  The beacon is the nicer mechanism and the desktop GCS uses it, but Apple's
  Local Network Privacy FAQ lists *receiving an incoming UDP broadcast* as
  requiring `com.apple.developer.networking.multicast`, which needs Apple's
  approval and is not available to a free personal team. That was unenforced on
  iOS 14/15 but is enforced from iOS 16, and the test phone runs 16.7.16.

  Unicast carries no such restriction — only the local-network prompt — and the
  board answers any datagram, so a /24 sweep finds it in well under a second.
  Sweeping takes the board's single UDP peer latch, same as connecting.
